    Comment lire ces résultats ?

    Une faible latence sur les seuls paquets livrés peut masquer de nombreuses pertes. Comparez toujours le p95, les pertes et la proportion de tous les messages reçus avant l’échéance. Le cloud ajoute ici un délai de transport ; ces profils ne décrivent pas tous les déploiements possibles.

    MODÈLE 1.0.0
    01

    Ce que l’application réalise

    Elle génère un trafic périodique de capteurs, calcule une file d’attente, applique des délais et des pertes, puis supervise deux lignes de production virtuelles. Elle permet l’arrêt et la reprise ordinaires d’une machine simulée.

    Elle ne contient ni liaison radio réelle, ni broker MQTT, ni implémentation Sparkplug B. Le bouton d’arrêt n’est pas une fonction de sécurité.

    02

    Un protocole reproductible

    120 capteurs par défaut, 5 messages par seconde chacun ; charge utile de 256 octets et surcharge supposée de 64 octets. La graine et l’indice de paquet déterminent la gigue et les pertes.

    Le comparateur observe 60 secondes d’émissions, puis termine la livraison des paquets encore en file. Les essais du rapport utilisent les graines 42 à 46.

    MODÈLE DE LATENCE

    L = attente + sérialisation + radio + cœur + transport + traitement + gigue

    File FIFO partagée ; rejet lorsque l’attente dépasse 100 ms. Gigue uniforme positive. Les pertes aléatoires sont indépendantes. Le modèle ne reproduit ni l’ordonnanceur NR, ni les retransmissions, ni une tranche réseau réelle.

    Hypothèses des profils

    La capacité représente un budget applicatif utile, pas une bande passante radio ni le débit maximal d’un standard. Surcharge de 64 octets : approximation pédagogique, pas mesure MQTT/TCP/TLS.

    Indicateurs

    p95 : rang ⌈0,95 × n⌉ des latences triées des paquets reçus.
    À l’heure : reçus en ≤ 50 ms / tous les émis.
    Pertes : abandons / tous les émis.
    TRS : disponibilité × performance × qualité.

    Cycle idéal : 1 s/pièce pour chaque machine. Le TRS décrit la production virtuelle connue par le simulateur, pas une mesure déduite d’un réseau réel.

    Du démonstrateur à l’usine

    Une version réelle ajouterait des capteurs, une passerelle, un broker MQTT authentifié, un hôte Sparkplug, des mesures horodatées et une validation radio sur site. L’interface web peut rester hébergée sur Vercel ; les fonctions industrielles restent dans l’environnement edge approprié.

    La supervision affichée devient « données périmées » après 3 secondes sans réception simulée ; ce seuil applicatif n’est pas le testament MQTT.
